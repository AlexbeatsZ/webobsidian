# 项目定位与 Obsidian 参考边界

## 目标与背景

本 fork 的目标是重建一个可以满足用户个性化需求的 Obsidian。现有 Obsidian
插件能提供部分定制能力，但用户希望修改的行为可能超出插件接口和宿主结构允许的范围。
本项目因此需要掌握应用本身的源码，让编辑、阅读、工作区、文件管理和界面交互都可以直接修改。

WebObsidian 是当前实现基础。浏览器、自托管服务和 Electron 桌面端是已有运行形态，
后续功能应围绕用户的实际工作流演进；复刻 Obsidian 的外观或扩大插件数量本身不作为完成标准。
具体个性化功能清单尚未确定，不能从这一背景推断用户已要求重写所有模块。

## 参考项目的用途

- [Obsidian 官方 API](https://github.com/obsidianmd/obsidian-api)：公开接口、对象职责、插件生命周期的首要参考。
- [obsidian-typings](https://github.com/obsidian-typings/obsidian-typings)：补充未公开接口的类型、注释和示例，
  用于理解内部对象关系、追踪目标插件依赖、建立行为差距清单。
- 用户明确指定的 Obsidian 行为：后续针对具体功能记录输入、操作和预期结果，作为实现验收依据。

obsidian-typings 以类型声明为主，也提供部分辅助实现；它不提供完整的编辑器、工作区或
插件宿主运行时。安装该包不会自动补齐这些能力。其维护者明确说明内部 API 的资料可能不完整、
不准确或随版本变化。因此引用具体接口时应记录对应 Obsidian 版本和参考分支或提交，
结合相关源码与实际行为确认，不能只凭类型检查通过认定兼容。

本次仅把该项目纳入设计参考，不增加 npm 依赖，也不选定全量插件兼容的目标版本。

## 实现原则

1. **个性化需求优先。** 先描述用户要完成的操作及现有障碍，再决定改动模块；
   必要时直接修改核心源码，不要求所有需求都通过 Obsidian 插件接口绕行实现。
2. **复用已有实现。** 在现有 React、CodeMirror、Node 服务和 Electron 壳上逐项补齐，
   不因项目定位调整而启动无关的整体重写。
3. **保留可迁移的数据。** 以 Markdown、附件和 JSON Canvas 等现有文件为基础；
   读取现有 vault 时保留未知配置和插件数据。文件格式兼容与 `.obsidian` 配置语义兼容分别记录。
4. **核心能力与插件适配分工。** 后续扩展时，让核心服务承载真实的文件、命令、工作区和元数据行为，
   兼容层将 Obsidian 接口映射到这些能力，避免为插件再维护一套相互脱节的状态。
5. **按需求建立兼容范围。** 优先支持用户实际依赖的插件和接口，不预先承诺所有社区插件、
   私有 DOM 结构或 Electron/Node 调用都能兼容。桌面与浏览器的能力差异需要明确记录。
6. **验收真实行为。** 插件可下载、可加载、方法存在、类型检查通过和实际工作流可用是不同层次；
   缺失能力不应靠空方法伪装成功。后续实现需明确报告不支持项，并验证注册、执行、持久化和卸载。

## 当前实现与差距

以下为 fork 定位初期的历史源码结论；2026-10-18 随后的插件宿主实现已替换该表中的空方法。
当前 API、现用插件版本及最终仅静态验证的边界以 [插件兼容设计](plugin-compatibility.md) 为准。

| 范围 | 当前入口与实现 | 后续关注点 |
| --- | --- | --- |
| 编辑与工作区 | `web/src/components/Editor.tsx`、`Workspace.tsx`、`web/src/lib/store.ts` | 已有编辑、标签页和分屏状态；后续按具体需求定义统一的工作区与编辑器接口 |
| 文件能力 | `server/src/services/vault.ts`、`web/src/lib/api.ts` | 复用既有文件服务；逐项确认兼容接口的返回值、状态刷新和事件语义 |
| 插件安装 | `server/src/services/plugins.ts` | 已有 manifest、资源安装与启用状态管理；安装成功不证明插件功能可用 |
| 插件运行 | `web/src/lib/plugins.ts` | 在页面中用 `new Function` 执行插件，`require` 仅支持 `obsidian`；这不构成独立的安全沙箱 |
| 命令、视图、设置 | 同上 | `addCommand`、`registerView`、`addSettingTab`、`saveData` 等为空实现，`loadData` 固定返回空对象 |
| 生命周期与元数据 | 同上 | `registerEvent`、`unload` 等未落实资源清理，`metadataCache` 只有基础事件对象，尚无对应元数据查询能力 |

## 后续推进顺序

以下为最初建议的推进顺序；首批插件盘点与兼容适配已经实施，完整用户工作流仍待验收。

1. 收集最先需要突破的 Obsidian 行为限制，以及必须保留的现有插件工作流。
2. 为首个需求列出“现状—目标行为—涉及模块—兼容影响—验收操作”，再进行功能修改。
3. 若需求涉及插件，先建立所需 API 的支持矩阵，再补真实行为，避免全量照抄内部类型。
4. 根据首批需求逐步完善命令与快捷键、编辑器扩展、工作区、元数据及插件生命周期。
   是否抽取独立服务取决于实际改动，不在本次文档调整中预设全面重构。
5. 每项交付分别记录源码与构建检查、隔离样例验证、用户真实 vault 和设备验收的状态。

首批对象已经确定为 Manage / STEM 当前安装的插件及各自版本；完整应用版本级别的
私有内部 API 等价性不作承诺。后续由统一验收中发现的具体工作流差异继续推进。
